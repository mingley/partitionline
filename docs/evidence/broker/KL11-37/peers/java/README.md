# Java OAuth peer source preparation

This is source preparation for actual Apache Kafka 4.1.2, 4.2.1 and 4.3.1 clients. It records no live broker or identity-provider success. The same source strict-compiles against all three official client jars and their already pinned distribution dependencies; compilation writes only small WORK class directories. No new dependency download or Cargo invocation is required.

`OAuthMetadataPeer` uses public `Admin`, `KafkaConsumer` and optional ordinary `KafkaProducer`. Its login callback subclass calls Apache `OAuthBearerLoginCallbackHandler` unchanged, configured with the official `ClientCredentialsJwtRetriever` and `OAuthBearerLoginModule`. The real retriever performs HTTPS client-credentials acquisition. A bounded public CA input becomes an ephemeral PKCS12 truststore shared by the broker TLS configuration and token endpoint's standard JAAS TLS options. HTTPS hostname checks remain enabled. The synthetic random client secret is read only from a bounded mode0600 file and never appears in argv, events or rendered retained configuration.

Commands arrive as bounded ASCII lines `query PHASE`, `recreate PHASE`, `write PHASE`, `read PHASE`, or `close PHASE`. Phase names contain only lowercase letters, digits, underscore and hyphen. There are at most25 commands. The control loop has a configured1–180second deadline, every public operation has an8second timeout, and each client close has a2second bound. An external owning driver must also impose an absolute process-group deadline, since SDK constructor/token refresh and multiple operations can outlast a control-loop deadline. Closing stdin alone does not request shutdown: the driver sends `close PHASE` and joins the process, with deadline fallback.

`query` executes actual public consumer `partitionsFor`/`listTopics` and admin `listTopics`/`describeTopics`. `recreate` closes the clients and creates fresh public clients with the same configuration before querying. It observes whatever token reuse/login-cache behavior the SDK actually implements; it does not claim every reconnect reacquires a token. Callback counters count only configuration, token callbacks, returned local token objects, extension callbacks, failures, and closes. A returned local token object does not establish broker acceptance. Allowlisted finite authentication/connection/request metrics are separate observations. Errors expose class names only, with no messages, stack traces, claims, credentials, bearer strings or private material.

The server's metadata profile has exactly6 APIs: Metadata3:0–13, SaslHandshake17:0–1, ApiVersions18:0–4, CreateTopics19:2–4, DeleteTopics20:1–6 and SaslAuthenticate36:0–2. It does not advertise API60. The server's explicitly selected ordinary read/write profile adds Produce0:3–13, Fetch1:4–6 and ListOffsets2:1–3 for9 APIs. The public SDK may choose supported request versions; protocol profile verification and server-side redacted request/correlation telemetry remain separate proof.

`write` is permitted only for a qualified ordinary read/write server. It lazily creates a genuine producer with `enable.idempotence=false`, null transactional ID, uncompressed records and acks=all (the declared RF1 local-durable profile). One synthetic keyed value includes exact timestamp1700000000123 and three ordered headers with duplicate/null/empty values. Its actual delivery offset is reported. `read` manually assigns partition0, obtains actual beginning/end offsets, seeks the beginning and polls the complete bounded ordinary history. It reports offsets, timestamps, key/value bytes and exact ordered headers, bounded to128 records and256byte individual fields. There are no groups, offset commits, transactions, idempotence, replication or compaction claims.

Root controls a fresh HTTPS issuer, outage/TTL/key-generation/revocation changes, broker restart, source-qualified binaries and deadlines. Future actual evidence must retain source/runtime/compiler/JAR pins, all failures, redacted token-endpoint/control counters, real API/correlation observations, fresh-client and same-client outcomes, process joins, and cross-peer read histories. Reauthentication remains out of scope; advertised session lifetime is zero.

Preparation attempt1 retained a strict deprecation failure for `KafkaConsumer.close(Duration)`. Attempt2 compiled the metadata-only draft. The final source uses `CloseOptions.timeout`; subsequent changes and their fresh strict compile are retained separately. Initial attempt1/2 receipts retain exact source hashes and logs; their prior source bytes were not copied at the time and are not retroactively reconstructed.
