# Broker finite-history audit

Read-only source review at commit `352c2a315720bb865cf4572edb459a087eef4370`.
The broker modules below are bounded foundations. A limit on *live state* can
be intentional backpressure; a limit on the number of journal records ever
written stops an otherwise healthy coordinator after sufficient routine
updates, including when its live state remains small. This review did not run
new fault or stress tests and does not establish end-to-end production behavior.
Existing evidence records local tests and their stated limitations; do not
replace or delete those records.

Cross-cutting check: several recovery loops call `Journal::fetch` with a fixed
16/32/64 entry count while their constructors accept smaller positive index
limits. `Journal::fetch` rejects a request above `max_index_entries`, so an
otherwise accepted low-limit configuration can fail even on open. Audit each
constructor/recovery pair and test its minimum legal limits; do not simply
raise limits. For snapshots, account for both live and temporary files during
atomic replacement, and validate that the encoded entry can be fetched after
restart. Keep ambiguous-write errors distinct from safe refusals and prevent
read APIs from returning unconfirmed in-memory state.
