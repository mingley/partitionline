# Raft vote dispatch and cancellation

The candidate is **not applied**. It changes one election-dispatch path so
each current vote is offered to its per-peer slot before the supervisor
waits for any displaced or unavailable vote to be canceled. The owner can
otherwise delay later peers' votes behind a full command queue. A full broker
run of the candidate still failed a Raft test, and the failure's cause is
unknown.

The production source baseline is main
[`c7a91ce50cd231bb7d85e90297d98344e5a98dec`](https://github.com/mingley/partitionline/commit/c7a91ce50cd231bb7d85e90297d98344e5a98dec).
The source candidate is
[`8865a7f41de51311db210885dc2175a6c4bc9e85`](https://github.com/mingley/partitionline/commit/8865a7f41de51311db210885dc2175a6c4bc9e85),
whose `partitionline-broker/src/raft/runtime.rs` Git blob is
`11840ff18f541b20e71e7507816c25baeebba144`. Temporary qualification
workflows and mutants are not part of that source commit.

## Behavior and controls

The existing supervisor's `Tick` produces at most one vote per peer. The
baseline dispatch loop offers a vote and awaits cancellation of any displaced
or unavailable job before moving to the next peer. The candidate first offers each job, keeping
displaced or unadmitted jobs in the already allocated input vector, and then
awaits their exact cancellations. It visits peers in reverse vector order;
the campaigns generated by the owner have unique peer keys. The code adds no
vector allocation. An in-flight RPC is unchanged and can still delay its
peer's newer vote.

A deterministic control holds a genuine storage owner after a state command
and fills its only command queue slot. It then polls the actual dispatch
future until its first cancellation blocks. On the baseline, only the first
route has the newer vote; the assertion that every current vote was offered
fails. On the candidate, all four live peer slots contain their current vote.
Dropping the pending future leaves these offered votes in the slots. This
is a forced queue schedule, not the explanation for an earlier Raft failure.

[Focused run 42468187896](https://github.com/mingley/partitionline/actions/runs/42468187896)
reproduced the baseline assertion failure and passed four focused controls in
each of default and all-feature profiles, including a current reply before
and after displaced cancellation and a higher-term stepdown. Its strict
all-target/all-feature Clippy passed. Its formatting step was diagnostic-only
and reported test formatting differences; it was not a format pass.

[Negative controls 42468793099](https://github.com/mingley/partitionline/actions/runs/42468793099)
made two isolated test mutations on the final source. Canceling the current
request instead of the displaced one produced `Node(InvalidPeer)` in the
current-reply control; omitting cancellation made an unavailable-route
response get accepted. Both intended tests failed and the workflow verified
those failures. The mutations are not applied.

An additional control exposes a remaining ownership gap: when dispatch is
dropped while cancellation is blocked, a current vote for a missing route
can remain registered in the owner until a later campaign or stepdown. The
control injects a genuine peer reply directly into the owner after the drop;
it does not claim the request was sent on the network. The candidate does not
make cancellation of unavailable routes safe against independent dispatch
abort, and it does not make peer transport authenticated.

## Full broker checks

[Run 42468517510](https://github.com/mingley/partitionline/actions/runs/42468517510)
tested the earlier candidate `f94eec7`: 775 default and 923 all-feature
tests passed, with four ignored in each profile. Its separate strict job
failed at formatting on two test-only differences, so Clippy, Rustdoc and
doctests were skipped in that job.

[Run 42468665977](https://github.com/mingley/partitionline/actions/runs/42468665977)
tested the final candidate blob listed above. The default profile passed
775 tests with four ignored, and all five focused controls passed in both
profiles. Formatting, strict all-target/all-feature Clippy, Rustdoc and
both doctest profiles passed. The all-feature library stopped at **528 passed,
one failed and four ignored**, so its later targets did not run.

The failing five-node TCP minority-partition/exit/restart/removal test sent
`fault-after-process-exit-proposal` to node 4 and received
`Node(NotLeader)`. Subsequent non-atomic diagnostics showed node 2 as
term-6 leader and node 4 as term-6 follower. They do not establish when
leadership changed, the cause, or whether this candidate contributed. The
proposal was not retried. The earlier all-feature pass does not qualify the
final source or explain the failure.

## Performance and pending work

The first [measurement run 42468600768](https://github.com/mingley/partitionline/actions/runs/42468600768)
built separate optimized binaries and completed 12 paired test invocations
per arm. Its sample-count gate failed because the empty-slot timing appeared
after libtest's `test ...` prefix while the gate required it at the start
of a line. Its empty-slot samples were also short, roughly 47–66 microseconds
per 200 dispatches. The raw output and
[artifact](https://github.com/mingley/partitionline/actions/runs/42468600768/artifacts/13611914126)
are retained; do not use this failed run as a performance pass or ranking.

A [loopback peer witness 42469274424](https://github.com/mingley/partitionline/actions/runs/42469274424)
used real outbound workers and two real peer owners while the source owner
and its one-slot command queue were held. In both candidate profiles, before
the gate was released, both peers' durable election state recorded term 3 and
`voted_for = Some(0)`. The held source owner could not process the replies
until released. The test-only baseline arm timed out after 2.02 seconds waiting for both
term-3 peer states; it did not capture exactly which earlier vote each peer
received. The baseline fixture is commit
[`4b6c156`](https://github.com/mingley/partitionline/commit/4b6c15658c9d3b22a82dd8efd804875cc5ccaf62);
the candidate fixture is
[`aee0448`](https://github.com/mingley/partitionline/commit/aee044853362accba6a252930a290aa4887d1415)
and adds test-only code to the candidate. This is a forced single-cluster
loopback schedule and does not explain the separate `NotLeader` failure.

[Matched comparison 42469111144](https://github.com/mingley/partitionline/actions/runs/42469111144)
used separate optimized builds on a shared four-vCPU x86 runner reporting an
Intel Xeon Platinum 8573C, stable Rust 1.99.1 and LLVM 23.1.1. It verified
that the measured dispatch functions matched the pinned baseline and final
candidate, required distinct binary hashes, and ran 12 alternating pairs.
Each process repeatedly dispatched four copied current requests through
in-memory slots. Empty slots used 1,000,000 dispatches per sample; full slots
used 2,000 and sent four exact stale cancellation commands per dispatch to
the real local owner. No peer network I/O occurred. Every individual measured
shape lasted at least 100 ms, and the parser checked both shapes and each test
result. Request-vector construction and slot reset were outside the timed
region; per-dispatch clock reads were inside it.

short local measurements on one shared runner. They do not establish election
