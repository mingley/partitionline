# WORK proposal: committed metadata application

This is a source-only implementation proposal based on actual main `3dbc216bf90fdd2527428335293b8c84a26e5e6e`. Nothing here has been installed on main or compiled. The old selected `e8fc0b7` design inputs and the accepted Runtime04/core47a bytes remain preserved. Root owns the eventual claim, export, source checkpoint and execution lease.

The missing connection was concrete: Metadata Router called the local Catalog journal directly, while autonomous Raft transported opaque records without an application consumer. The proposed explicit `Router::open_quorum` now owns a quorum-backed Catalog on the existing joined blocking actor. Its mutations call `QuorumCatalog::execute_until`: refresh source commit → fence request identity → propose canonical command → wait for that exact term/index → consume committed records → synchronize the application receipt → publish a prepared catalog change. A timed-out command is ambiguous, not rolled back. Typed callers retain RequestId across retries; Kafka requests receive a generated token for their one server-side attempt.

Every source position gets a receipt, including barriers and voter records. The receipt stores exact term/index/kind/full payload, protected by the existing Journal framing/CRC. Startup rebuilds nothing visible until every prior receipt has matched the actual committed source prefix. The application therefore detects a wrong term, altered payload, gap, foreign genesis/group, changed semantic limits, and an application cursor ahead of the source. A complete synced receipt before projection publication is replayed once. Incomplete final Journal entries use the existing synchronized tail-repair contract; complete corruption fails closed.

Commands are deterministic. An otherwise valid create/delete that loses a semantic race commits a no-op result such as DuplicateName; it does not make the replicated history unreplayable. Exact duplicate RequestId+bytes returns the first decision. Conflicting reuse is a committed no-op if it appears in the log, and is rejected before a new proposal by the typed adapter. IDs, rejected decisions and tombstones remain finite and are not evicted in a way that would weaken retry fencing.

Catalog exposes an explicit Projection which reuses its existing name, UUID, collision and resource rules. The default local Catalog path and its public create/delete receipt types remain. Direct create/delete on a quorum Catalog rejects QuorumMode, so a new mode cannot bypass source admission. Router's two mutation sites call private backend-aware operations; all old store constructors select the local backend. The new frontend attaches no Produce/Fetch data Store and raises no API cap. Its Metadata controller ID comes from observed source leadership. Existing single-broker logical partition placement is retained and is not replicated data placement.

The adapter uses the existing blocking owner: it adds no task/channel/socket/DNS admission. Runtime getters proposed in the separate runtime draft return only immutable configured group/genesis and storage limits; Node/WAL/election/transport behavior and reviewed core47a are untouched. Application limits bound positions ≤4096, individual source payload ≤1MiB, cumulative payload ≤64MiB, application Journal bytes/index/fetch, request decision tables and catalog state. Checked arithmetic charges tables, payload copies and fetch scratch. Allocator overhead, OS buffers/RSS, existing Runtime budget and caller-retained results remain separate. Async source calls share one absolute deadline; filesystem synchronization is not cancelable or bounded by that timer. Successful shutdown must join the application actor before shutting down Runtime.

There are nine proposed application/core unit cases and two proposed real 3/5-node TCP Router cases. Unit sources cover exact retries/reopen, racing commands/token conflict, receipt term/payload/gap, group/limit/legacy-format rejection, malformed/budget preflight, complete receipt before publish with incomplete-tail repair, 3/5-node majority visibility/minority/reopen, and new-leader truncation of uncommitted metadata. TCP sources drive compiled CreateTopics/Metadata payloads through Router, require majority writes after stopping a minority, restart those replicas and refresh their views, reject a follower create, and join both actor and Runtime with actual zero network ownership checks. These are declared test sources; executed case count is zero.

Before qualification, Root must review/claim the five proposed source/test paths, export `metadata_quorum`, reconcile any newer source changes, publish a whole-source pin, grant compiler/disk leases, and run the real stable/MSRV feature and wire regression gates. An independent reader must bind actual application receipts to source committed records and decode new handler outputs. Full 76 TCP fault/image/lifecycle qualification remains open; these sources do not substitute for it.

Limits remain explicit: request-driven application refresh; committed-prefix reads without a linearizable read barrier; custom private command/application formats, not native Kafka metadata records or KRaft wire; fixed configured trusted peer discovery; no replicated data partition placement/physical Store attachment; no physical log/application compaction; no claim of production, security, native Kafka replication or performance qualification.
