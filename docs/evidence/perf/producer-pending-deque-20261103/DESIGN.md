# Producer pending-queue design

This is a source-level design, not a patch or a measured result. It targets the exact v14 fixed client sources identified in `receipt.json`. It does not establish the cause of the retained-backing failure, a speedup, production readiness, or a fastest-performance claim.

It configures `batch_records(1)` and `max_in_flight(1)`, so the client must send the accepted records as separate, serial request/acknowledgement cycles. The client requires TCP_NODELAY to succeed; the mock attempts to set it but discards errors. The effective socket options were not measured. ## Work to measure

`Worker.pending` is a `Vec<Pending>`, and `fill_spare` fills the reusable batch with `pending.drain(..n)`. Removing a prefix preserves the order of the suffix by shifting the suffix. For a fixed queue of N records, drained one at a time with no additions, the logical tail-position changes sum to N(N-1)/2: 8,386,560 for N=4,096. This is a complexity deduction, not a measurement of bytes copied or the time spent in the hosted test. In particular, the real queue length changes as the worker and channel progress, and 4,096 network round trips may dominate. The v14 ordered-deadline hint avoids some deadline rescans, but the prefix shifts remain. When deadlines are nonmonotonic and the removed record is the cached minimum, suffix scans can still be quadratic; a deque by itself does not change that.

## Candidate representation and scope

Use a worker-owned `VecDeque<Pending>` for the logical pending FIFO. Front removal and back insertion avoid moving the remaining elements in steady state; growth may relocate elements and is amortized. Reuse a separate `Vec<Pending>` for the immediately returned batch. Keep `preparing`, `completing`, response and retry ownership stages unchanged in meaning. Avoid `make_contiguous` on the normal send path: repeatedly linearizing a wrapped deque would recreate the original cost. Read-only routines (`take_count_in`, leading sequence counts, sticky counts, expiry searches and deadline/stat folds) should iterate logical order across both deque slices and preserve their existing cooperative-yield cadence. Bench generated code and allocation behavior; generic iterators should not be assumed faster.

Tokio `Receiver::recv_many` takes a `Vec`, not a deque. A bounded worker-owned receive scratch vector can receive a chunk and transfer it to the back of the deque in original order. Every accepted record must remain in either the channel, this worker field or the pending deque; no payload may live only inside an awaitable's local variable when cancellation can drop it. If chunk transfer yields, mark pending statistics invalid before transfer, persist transfer progress in the Worker, and restore/requeue/fail both deque and scratch in their original order on drop. If transfer is deliberately synchronous, bound the chunk and verify worst-case scheduler latency. Changing receive chunk sizes can alter grouping, linger timing, backpressure and fairness even with the same configured limits; compare actual behavior rather than assuming compatibility. On every exit from an invalid accounting state, repair it before a batch decision, expiry decision or timer calculation. Tokio 1.53.3 documents that if another `select!` branch wins, the canceled `recv_many` receives no messages. Separately, after a successful receive, scratch must already be Worker-owned through every later await; controls should exercise both that documented select case and cancellation after successful receipt.

For a prefix drain, compute the removed estimate and any needed minimum deadline while all records are still in the Worker. At the synchronous commit point, move the front records into the reusable batch, update the cached estimate/deadline and transfer the batch into `Preparing` without an intervening await. No live `VecDeque::Drain` may cross an await or escape. A large synchronous move is O(batch size), so it does not by itself bound scheduler latency; use a bounded policy or a chunked Worker-owned commit stage if a configured batch can be large. Preserve batch size/byte limits, topic/partition grouping, `batch_base_seq` and record order, and do not change the policy for ambiguous writes or retry sequencing.

## Split, expiry and cancellation

`Split` currently tracks stable classification, permutations, selected records and rollback for ordinary expiry and sticky batches. Port it to logical deque indexing and `swap`; do not move ownership into a temporary iterator across a yield. One possible suffix extraction after the tracked permutation is to pop from the back in bounded chunks into a Worker-owned selected buffer, retaining a stage and orientation marker. Back-popping leaves the selected buffer in reverse logical order. Before exposing a successful selection, restore its forward order; if reversal is cooperative, store its stage and completed swap positions so cancellation can undo the partial reversal. On cancellation, first restore the extraction orientation, append the selected elements back into the unchanged-capacity deque in original suffix order, then apply the tracked inverse permutation before newer receive-scratch/channel records. Reserve all storage needed for rollback before a phase that can suspend, verify that pop operations do not shrink it, and leave callback and byte ownership with exactly one stage. The existing sticky singleton path also owns its removed front record in `Split` while earliest-deadline refresh can yield; a canceled operation must restore that singleton ahead of newer records. This is a design to verify, not a claim that the existing `Vec::split_off` capacity assumptions automatically hold for `VecDeque`.

The sticky batch path calls `pull_ready` while holding the cluster lock and sticky-policy lock, then checks membership and seals the selected tag. A chunked receive policy must preserve the cohort and ordering visible at that boundary and never yield while either synchronous lock is held. One possible approach is cooperative pre-draining outside the locks followed by a synchronous boundary drain under the existing lock order, but its bound and concurrent-admission semantics need proof; if that cannot be established, retain the old behavior until the protocol is redesigned.

Keep duplicate deadlines and nonmonotonic retry insertion correct. The cached earliest deadline must reflect all logical pending records, including any receive scratch that can be used for scheduling; if accounting is uncertain, mark it invalid and rebuild before selecting. For ordered deadlines, the new front remains a valid minimum after a prefix drain. For other orders, retain the conservative current rescan when the removed prefix included the minimum. A later indexed deadline structure could reduce this conditional worst case, but it must be bounded, handle duplicate deadlines and stable arbitrary expiry removals, and remain correct through split, rollback, retry, compaction and cancellation; lazy tombstones alone can grow without bound.

On Worker drop, restore any active split and retire all worker-owned records in the same order and with the same error/retry rules as today. Restoration and synchronous Drop can be O(queue size); neither deque nor ownership alone bounds scheduler latency. A deferred cleanup design would need its own durable bounded owner, exact-once completion and runtime-shutdown contract, so measure responsiveness and do not assume Drop may await. In-flight and partially written groups keep their existing ambiguous-outcome handling. Record-byte reservations, sticky membership, delivery callbacks and live-worker accounting each transfer or release exactly once. Verify actual `recv_many` cancellation and all cooperative-yield boundaries rather than modeling only a manually filled queue.

A deque does not impose a whole-producer memory bound. The present byte budget counts selected record bytes and `buffer_memory(0)` explicitly disables that cap. Zero-byte records can pass a nonzero byte budget without consuming it, `pull_ready` can move channel records into the worker, and `send_all` first materializes its input. A production resource policy needs a separate producer-wide live-record/object and framework-owned byte budget, including queued, scratch, preparing, in-flight and retry states, plus bounded auxiliary indexes and retained capacity. Define the observable backpressure/compatibility behavior before implementing that policy; memory supplied and retained by callers is outside the producer's control.

## Required controls and qualification

- Preserve every v14 test identity, threshold and assertion, including the original retained-backing control. Separately repair its unrelated deadline-scan control fixture only by forcing the nonmonotonic suffix it was intended to exercise.
- Exercise a wraparound deque with distinct record identities: repeated append/front drain across both physical slices, mixed topics/partitions, retry batch sequence boundaries, all/none/interleaved split selection, including cancellation partway through selected-buffer reversal, sticky batches, equal and inverted deadlines, timer expiry and recovery after emptying.
- At each actual yield in receive accounting, suffix scans, split construction/permutation/extraction, preparing and response handling, cancel or shut down the Worker. Verify old/new FIFO, all received records, sequence ownership, reservation totals, delivery results, callbacks, retry counts, worker count and retained descriptors. Test both open and closed producer paths and the real receiver boundary, not just a manually edited deque.
- Count observed logical tail relocations or instrument the actual queue operation, and independently assert record identities and order. The 4,096 single-record drain should show the old triangular work and no per-drain relocation of surviving deque elements; account for growth and split separately. A correctness test must not infer byte movement solely from an expected formula.
- Run the unchanged retained-backing test with the same 2-second admission, 10-second flush and 15-second delivery limits on exact source pins under both feature profiles; retain full failure text. Observe actual requests and acknowledgements, not only mock append counts, and collect bounded, nonblocking diagnostics without changing success behavior.
- Compare exact preimage/candidate in optimized builds on controlled x86 hardware: isolated queue microbenchmarks, one-record and normal-batch end-to-end workloads, cold/warm capacity, varying queue depth, retries/expiry/sticky cases, p50/p99 latency, throughput, CPU and peak allocations. Report runner, Rust/LLVM version, settings, repetitions and raw results; keep a live Kafka interoperability run distinct. Recheck consumer/control responsiveness under load. No result establishes a world-fastest claim without a fair, reproducible comparison against the named alternatives.
