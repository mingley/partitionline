# Producer handshake and retained-backing audit

This audit describes the exact v10 candidate checkout `b1b0488096f886c2fd60a7368bbf2ed57b5da2e3`, source specification SHA-256 `3286ffa57a68cef353b2a09728924f6cc3710e634a2f98954246aa44ad94b2a5`. Its native qualification ran on x86 in GitHub Actions run `41574318102`, job `125714639741`; the original artifact SHA-256 was `1826243e647733370d2976076912de728991a2075e1e16e5f55c1c906149bce6`. The report is scoped to that candidate and those tests. Both feature profiles passed the library suite and strict Clippy, and failed the same 15 `mock_produce` tests (32 passed). The retained-backing fixture timed out after 10 seconds in both profiles (8 passed, 1 failed, 1 ignored). No other test or configuration is implied to pass.

The original test `send_all_redials_leaders_while_refreshing_metadata` sets `connections_max_idle` to 40 ms, sleeps 60 ms, delays ApiVersions and Metadata responses by 250 ms each, and asserts completion in under 450 ms. In this trace the replacement metadata socket negotiates first, then sends Metadata: the two configured delays are sequential. Metadata alone completes at 503.609 ms, even though the first leader handshakes overlap it. The all-features trace likewise completes metadata at 504.006 ms. The threshold therefore conflicts with the source's current requirement to negotiate the replacement metadata socket before sending Metadata. The test and its threshold remain unchanged. A separate candidate control `send_all_redial_handshakes_overlap_before_metadata_response` checks the intended concurrent handshake phase and verifies the actual application sockets' ApiVersions, but does not make the original assertion pass.

After the speculative leader handshakes completed, their sockets sat unused while Metadata was outstanding for another 252 ms, longer than the configured 40 ms idle limit. The observed implementation then opened and negotiated another leader pair, closed the first pair, and sent Produce. This is real extra work, but its significance and a safe way to retain or overlap those sockets require further work: the trace by itself does not establish that respecting the idle policy is a defect, or quantify its effect in production. A change must consider idle policy, stale metadata, cancellation, physical socket retirement and SASL session ownership.

There is a separate compatibility conflict among the old count assertions. `transactional_startup_skips_a_second_bootstrap_handshake` requires one ApiVersions request at startup on a single broker; `idle_coordinator_socket_drops_when_the_broker_stops_writing` requires at least two simultaneously open metadata/coordinator sockets. The candidate creates a separately negotiated and authenticated physical connection for each role, so those two expectations cannot both describe that implementation. Sharing one real socket requires safe multiplexing/ownership, while transferring a previous socket's authentication state to a new socket is invalid. A broker replacement can also advertise different API ranges at the same address. This is a fixture/implementation contract conflict, not proof that every listed failure is unavoidable.

One concrete opportunity is independent of the contradictory count assertions: `group_coord_roundtrip` discovers a group coordinator into a local connection and drops it after each offset-commit call. Repeated requests for the same group thus make new connections and handshakes even when a real prior coordinator connection could be kept alive. Safe reuse needs an explicitly bounded live-connection cache keyed by the group, response correlation and cancellation safety, idle and session expiry handling, retriable-coordinator errors, physical retirement, and shutdown behavior. This report does not claim such a cache has been implemented or measured.

The retained-backing fixture was not explained by the handshake trace. It gates an initial Produce response, admits thousands of records with one record per batch, cancels the sender, releases the gate, then times out waiting at most 10 seconds for `flush`. Pending queue scans and vector prefix shifts are plausible costs, but their relative contribution has not been measured. The independent v2 pending-queue candidate has not been qualified by this run. A native test and focused benchmark are required before attributing or claiming improvement.
