# Live compatibility stack investigation

This bundle records the observed failure at commit `2645e96ce693fcdaa9d8c56f6f0c910934fd19a2` and prepares experiments. It does not contain a qualified fix. It does not change the repository or the live test's deadlines and assertions.

## What was observed

GitHub jobs `125774457011`, `125774457154`, and `125774457229` for Kafka 4.3.1, 4.2.1, and 4.1.2 respectively reached the admin, produce, manual-consumer, and groups phases. Each printed `compatibility group phase: classic join`, then reported `live_compatibility_required` stack overflow and SIGABRT. The logs identify no stack frame or last completed RPC, so they do not establish which future or operation consumed the stack. These jobs used Linux x86_64, rustc 1.99.1, and the unoptimized test profile with debug information disabled. The retained `connector-decoded-job-*.log` files are UTF-8 re-encodings of the connector's decoded log strings; their hashes are not hashes of the server's original compressed logs.

An earlier 2 MiB mock group-lifecycle control passed in the v16 baseline and both fixed profiles. Its `group.rs` inputs differed from 2645 and it did not execute the full live compatibility caller. An older retained debug executable also had large join/rejoin/assignment poll prologues, but it was built from a different source graph. Neither observation establishes a frame size or root cause for 2645.

## Source ownership and hypotheses

The live test awaits `run()` under a 150-second timeout. Its group loop awaits `join_group` under that helper's existing 20-second timeout, then calls a public classic join with the configured three-second request timeout. Classic join reaches the already boxed `join_with_protocol_list`, which awaits `rejoin_within`, then an unboxed `rejoin_once`; that future also awaits `assign_committed` after the group assignment. Other branches and concurrent metadata/RPC futures can be present in the state machine. The printed phase does not show which of these paths was polled or completed when the stack overflowed.

The state stored in an async future and the stack consumed when constructing or polling it are different quantities. Tokio 1.53.3's `Runtime::block_on` boxes a large outer future in debug builds, but construction can still create stack temporaries, and boxed inner futures can still have large poll frames. Compiler lowering, inlining, current thread stack, cancellation and earlier phases all affect the actual call chain. The live test's stack mapping was not measured; do not infer it solely from the usual 2 MiB libtest setting.

## Separated experiments

- `future-size-diagnostic.patch` only appends an ignored test to the original compatibility target. In a diagnostic 8 MiB thread it constructs, measures with `size_of_val`, and drops the real `run`, `join_group` and public join futures without polling or networking. Invoke it explicitly with `cargo +stable test --locked --test broker_compatibility -- --exact report_compatibility_future_state_sizes --ignored --nocapture`. It reports state sizes and a completion marker. Those sizes are not a bound on construction, poll or drop stack usage; adding a test can alter binary layout and code generation.
- `phase-trace-diagnostic.patch` inserts stderr phase markers in a diagnostic-only library build around initial connect, rejoin, and assignment. Logging itself changes execution, stack and timing. Use marker order to narrow a hypothesis, not as proof of the uninstrumented call stack. Do not ship these logs as a fix.
- `caller-box-experiment.patch` boxes the group-loop helper future in the compatibility test only. It adds a test-side allocation and does not change the application library or establish production stack safety.
- `library-box-experiment.patch` boxes the private `rejoin_once` future once per rejoin attempt. It uses the existing deadline and same future, with no spawned task, but adds a heap allocation and changes layout and allocation-failure behavior. A boxed future can still require a large temporary or poll frame. This is a source experiment, not an established fix or a performance improvement.
- `prior-two-mib-mock-control.patch` is the unchanged previously prepared child-process test exercising real group lifecycle calls against the mock on a 2 MiB thread. Its earlier passes were on different source, and even a current-source pass would not reproduce the full live caller.
- `inspect-elf.py` hashes the input before and after validating its ELF64 little-endian x86_64 executable/PIE header and again after inspection; it saves the tool versions, symbol listing, and raw first 192 bytes of selected symbols using `nm` and `objdump`. The separate file opens and matching hashes cannot exclude a replace-and-restore race. Supply a private snapshot with no concurrent writers and retain its hash; this tool does not enforce snapshot isolation against a hostile writer. Missing/inlined symbols make the measurement incomplete. Prologues do not prove the maximum live stack or establish the crashing call chain.

## Hosted comparison needed

On the same x86_64 host and toolchain/profile, build exact 2645 source and record the executable hash. First repeat the unchanged live test with its ordinary environment and a fresh digest-pinned broker and namespace. Then compare unchanged source with per-process `RUST_MIN_STACK` of 2 MiB and 8 MiB, each on a fresh equivalent broker/namespace, using the same 150-second outer test deadline and all original assertions. `RUST_MIN_STACK` affects threads created by that process; record the actual thread configuration or mapping where possible. The larger stack is a diagnostic intervention, not a production fix or a replacement CI gate. Separate these from concurrent host load and retain the original job outputs.

Run the phase trace in another fresh cell and record the last marker. Measure future state sizes separately; no output is a positive result unless the diagnostic completion marker and exit status are both present. Retain the actual test ELF and raw disassembly for each source variant. If baseline does not reproduce the original failure, or a trace changes it, record that as inconclusive rather than silently substituting the altered run.

Compare caller-only, library-only and, if needed, combined experiments against the same unchanged baseline and stack settings. Require the original complete live compatibility scenario and its existing assertions to pass under the normal test environment before considering any candidate; check all three Kafka versions on x86_64, plus focused group startup/cancellation/deadline and 2 MiB mock controls. Preserve every timeout, use guarded child processes and bounded artifact retention with core dumps disabled, and retain source/lock/toolchain hashes. Check the library experiment's allocation and group rejoin impact before any performance conclusion. Diagnostic-only traces and explicit larger stacks cannot count as the final fix.
