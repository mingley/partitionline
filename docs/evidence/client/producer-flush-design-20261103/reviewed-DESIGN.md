# Producer flush lifecycle: design draft

This is a design and an isolated, uncompiled accounting sketch. It is not a producer fix or a performance result. The findings in the [flush controls report](../producer-flush-controls-20261103/REPORT.md) are pinned to `45cbff24de76490594970fc962cd04e7be9fafb1`. At `86f285c706645e68146737a243707953c524b89d`, `src/producer.rs` SHA-256 is `eb7d6067c3c1e9e1ddfc8c3c140cfc16a889da250429a884c1805f41f13e38d1`; its diff from the tested source changes documentation only. This proposal needs independent concurrency review, implementation, native tests and measurement.

## Contract and invariants

A flush that returns `Ok(())` covers every record whose admission linearized before that flush's cutoff. Each such record must have a terminal local outcome, its reserved resources released, its required interceptor invocation handled, and its per-record result published or its receiver observed closed. With `acks=0`, success means the complete local write, not broker acknowledgement. Later records need not delay an ordinary flush. An error result may represent one or more delivery failures; it does not imply that those failures were successfully delivered. The caller-selected deadline and a record delivery timeout both remain public `Error::Timeout`, but they must remain distinct through all internal drain and transaction callers. Existing `close`/`close_timeout` public mapping, which only returns `Timeout`, stays unchanged unless intentionally changed separately.

Use an internal result such as `Drained { delivery_error: Option<Error> }`, `DeadlineExpired`, or `ClosedBeforeDrain` and convert to `Error` only at the public boundary. A record's delivery `Timeout` or `Closed` inside a fully `Drained` result must not be mistaken for an unfinished drain. `drain_before_abort` currently calls public `flush()` and treats either `Error::Timeout` or `Error::Closed` as a reason not to send `EndTxn`; with newly visible delivery failures that would incorrectly block an otherwise safe abort. The proposed internal abort path must proceed after a fully drained delivery failure (subject to fatal-transaction checks), and must stop on an actual drain deadline or closure before completion. This changes that existing edge behavior and needs targeted tests. Commit still rejects a drained delivery failure. Close must preserve its existing mapping deliberately, including a drained delivery `Timeout`, rather than accidentally changing results by erasing the internal distinction early.

Every accepted record owns exactly one completion ticket and a resource reservation. The ticket follows the record through the worker's data channel, pending batches, socket in-flight state, any retry transfer, a retired worker and terminal cleanup. Retries transfer the same ticket; they never create another. Rejected sends and admission futures dropped before commitment have no ticket and must not create a failure for a flush. A zero-byte record still owns a ticket. A successful enqueue must not be visible to a worker before that ticket and the resource lease are in the record. Terminal work publishes any failure before the ticket's outstanding count is decremented. No other signal, including `buffered_bytes`, worker snapshots, task counts or `retries_out`, proves completion.

## Admission and cutoff

Use an `Arc` generation with one atomic word containing a sealed bit and a checked outstanding-record count. The current open generation is published through a safe atomic-`Arc` facility such as `arc-swap`; the dependency, its unsafe internals and its hot-path cost require review. Rust's standard library does not provide a general safe atomic `Arc`; a `RwLock<Arc<_>>` is a simpler correctness-first alternative but adds a lock to every initial record admission. No speed claim is warranted for either choice.

For initial admission, first obtain the actual Tokio channel permit and all admission/buffer reservations. Under the existing `WorkerAdmission.commit` lock, recheck worker and producer closure, then CAS-increment the open generation only if its sealed bit is clear. Attach the resulting non-cloneable ticket and resource lease to the record. The successful CAS is the admission linearization point: from there the owned permit's synchronous `send` must be infallible and contain no await or user callback. An admission that cannot obtain a permit, observes closure or fails the CAS returns its reservations without a ticket; its caller may retry. Treat an impossible panic between committed CAS and permit handoff as a separately tested failure path, not as an excuse to leak the count. `try_send` may return a transient `QueueFull` when it races a rotation. An async admission enables its generation-change notification before the relevant state check, drops any channel permit and worker lock after a failed attempt, and then re-reads both the published state and a monotonic generation-change sequence before deciding to await within the existing max-block deadline. Seal, replacement, pause, reopen and close must advance the sequence and notify. Re-reading only pointer identity is insufficient because a cancelled fallback can reopen the same `Arc`; re-reading before registering is also insufficient because `notify_waiters` does not save a missed wake. No spinning or waiting while holding `WorkerAdmission.commit` is allowed. Sticky and non-sticky sends use the same final handoff; record rerouting with an existing ticket bypasses registration.

A flush serializes rotations under a short control-plane mutex. It seals the current generation by an atomic read-modify-write, then publishes a new open generation. That sealing operation is the cutoff: a concurrent registration CAS either precedes the seal and is counted, or observes the sealed bit and retries on the next generation. A producer close publishes a permanent closed sentinel instead of a new generation, so a sender that passed an earlier `closed` check cannot register after the close cutoff. This closes admission at the start of `close`, whereas the current code begins shutdown after attempting flush; that change needs public API and concurrency review. The brief sealed-to-published interval must not make `try_send` wait. The atomic count must reject overflow, never wrap. Use acquire/release ordering around registration, sealing and completion; the last completion notifies waiters only after result and failure publication. The model sketch illustrates the single-generation CAS and accounting, not the full `Arc` publication protocol.

A generation waiter must create and enable its Tokio `Notify::notified` future before checking the sealed count, then await only if the count is nonzero. This avoids losing `notify_waiters` between the check and registration. Cancellation of that notification future must not change the generation or reporting cursor.

A flush must also cause queued work to progress. A broadcast wake signal and monotonic flush-request counter are needed for records the worker already holds: register for notification before the final counter/state recheck, and promptly drain when the counter advances. They are **not sufficient** by themselves. A sender can register before the cutoff, pause before `Permit::send`, and let the worker consume the broadcast while its channel is empty. Therefore, on every dequeue, the worker must inspect the record ticket's generation and initiate prompt draining if it is sealed, even when its wake counter has not changed. If dequeue occurs before sealing, the subsequent wake/counter path must instead force the already-held record. This includes a ticket-bearing retry reaching a worker after the wake. A worker may drain later work too; that does not change the cutoff. A canceled capacity-fallback flush may reopen its epoch, so a reopened ticket no longer needs that fallback's immediate drain. Retried records continue their normal retry/deadline rules. Prove that the combination covers every owner in the actual worker and retry lifecycle before removing `Ctrl::Flush`; neither an atomic counter nor an observed channel send alone proves a record completed.

## Completion and cancellation

A ticket on its own cannot release a record's bytes, sticky state, callback, or oneshot: marking the count finished in `Drop` while those duties remain would let a flush succeed too early. Refactor ownership so an unfinished `PendingOwner` owns `Option<RecordData>`, its resource lease, result sender and ticket. Its terminal method performs exactly one disposition; a cancellation or panic in any async helper leaves an owner for every unprocessed record. Rust `Drop` makes direct moves from the existing `Pending` illegal, so convert moving fields to explicit `Option::take`/guarded transitions. Never take a batch out of a guard across an await unless a replacement guard owns the complete suffix. This applies to `detach_pending_chunks`, `fail_kept_pendings`, `requeue_pendings`, `InFlightGuard`, retry guards and the success/`acks=0` loops.

For common completed batches, aggregate resource and generation decrements by contiguous generation where possible, but use a batch guard that owns all transferred, not-yet-decremented tickets. There must be no await or fallible user code between transferring each completed ticket and establishing that guard. Its drop must settle both processed and unprocessed suffixes exactly once. A mixed-generation batch may use a bounded small map or split runs; benchmark the alternatives. A plain pre-decrement followed by callbacks is incorrect, as is disarming every ticket before the batch decrement is itself owned.

Cancellation cleanup must not call arbitrary interceptors while holding the worker, metadata, sticky-policy or generation locks. A bounded cleanup supervisor with capacity reserved at admission can receive abandoned owners without waiting; its ownership graph must avoid `Shared -> queue -> Pending -> Shared` cycles. One possible split is `Shared -> producer queues` and `Pending -> Arc<CompletionDomain>`, where the domain contains budgets, generation and callback resources but no queue sender/task back-reference. If a supervisor is unavailable or the runtime is shutting down, an explicitly designed synchronous fallback must still release resources and publish a terminal result; it may be expensive on large drops and must be measured. Alternatively, fail the producer closed and retain the ticket until a guaranteed cleanup owner takes it, but do not mark cleanup complete prematurely. Queue-reservation, fallback, worker teardown and panicking interceptor behavior are unresolved implementation work, not properties of the sketch.

Intercepting a callback panic with `catch_unwind` is necessary if unwind panics are to be isolated per callback; it does not protect against `panic=abort`, an indefinitely blocking callback, or a panic while dropping a panic payload. Choose and document whether interceptor failure is reported separately from a successful broker acknowledgement so users are not encouraged to resend an already-written record. Callbacks must be invoked without producer locks, must not run twice after cancellation, and need a reentrancy/deadlock policy. A blocking callback can delay a flush until its own deadline. Completion order is: decide broker/local-write outcome; safely settle sticky and byte ownership and metrics; invoke/handle the callback; send or observe the per-record oneshot; publish a failure if applicable; finally decrement the generation. Exact ordering among the first four may be adjusted only if the same ownership and visibility guarantees hold.

## Error reporting and overlapping flushes

Each generation stores the first terminal failure that it publishes and a saturating count; the failure path may take a mutex and retain a bounded error value. This is one representative error per generation, not a promise to enumerate every failed record. Per-record `send`/`send_all` results and interceptors remain the detailed channel; failures can also be reported by flush. Error selection within a generation is first *published*, not necessarily earliest admission. Across generations choose the earliest unacknowledged generation with an error. Document that multiple failures covered by one completed flush are acknowledged together and the public error does not include their count unless the API is extended.

Maintain a producer-wide acknowledged generation cursor under the rotation mutex. At cutoff, each flush snapshots the cursor and holds references to the sealed generations it must wait for. On completion, it inspects all covered results and advances the cursor through its own cutoff in the same synchronous poll that returns `Ready`, with no await between claiming errors and returning. If the deadline wins or the future is dropped before that point, it advances nothing. Two overlapping flushes that both captured an error before either acknowledgment can both return it, even if the later-cutoff flush returns first; a flush whose snapshot starts after acknowledgment does not report it again. A completed result that the caller discards is considered observed. A later-generation failure is never swallowed by an earlier cutoff. If another overlapping flush actually returns an error while the first is cancelled, that other flush may legitimately acknowledge it. The cursor can advance only over fully complete covered generations.

## Bounds and stalled flushes

Generations are allocated only on flush rotations, never per record. Put explicit finite bounds on retained generations and simultaneous active flushes, with a deadline-aware semaphore for the latter. Flush handles may each hold at most the generation bound in `Arc`s; document the aggregate bound and account for them even after ledger pruning. A separate global accepted-record limit is needed for an absolute object/cleanup bound because byte limits permit zero-byte records and unlimited-buffer mode. It should be configurable, checked before commitment, and preserve the distinction between temporary `QueueFull`, max-block timeout and delivery timeout. This is a behavior/configuration change; choose and measure the default rather than silently asserting an existing limit. The limit may cost another atomic reservation per admission.

A generation cap must not make future flushes impossible after earlier callers time out. At the cap, a bounded fallback can seal the current generation and temporarily publish a paused sentinel instead of allocating another generation. New initial admissions fail fast or wait outside all locks; existing ticket-bearing retries still proceed. Fallback flushes share that sealed cutoff and wait for every covered ticket. If the last fallback waiter times out or is cancelled before acknowledgment, synchronously reopen that same unacknowledged current generation and wake admissions; earlier regular flushes cannot cover it because it was open before this fallback. If one fallback completes, it acknowledges the completed range, replaces the current epoch and then unpauses. Closing the producer overrides reopening. Each fallback guard needs an epoch-specific identity so dropping a stale guard after an earlier fallback completed cannot reopen or alter a newer generation. These transitions need a single control-plane lock, waiter reference counts, and model checking for attach/cancel/close races; do not adopt this fallback based on the sketch alone. A timeout bounds the pause, but a stalled record can still cause a requested flush to time out. Continuous later traffic cannot indefinitely postpone an ordinary cutoff.

## Required deterministic checks

1. Race a registered admission against sealing on both sides of the CAS; assert every accepted record before cutoff is included and no rejected record creates an error. Stop a sender after it registers but before `Permit::send`, seal and broadcast, poll the worker until it has consumed the wake with an empty channel, then allow handoff and prove the sealed ticket forces immediate drain despite a long linger. Also reverse dequeue/seal order and repeat on a retry. Stop a sender after acquiring a channel permit, then race worker retirement and close. Include async cancellation before and after handoff and a full/closed queue.
2. Complete later records first, across multiple workers and retries; an early pending zero-byte record must still block `Ok(())`. Later admissions must not delay a normal cutoff. Exercise success, broker failure, delivery timeout, `acks=0`, empty input and partially accepted `send_all`.
3. Cancel after flush registers, after its wake is sent, immediately before/after each outcome publication, and before the final `Ready`; verify no canceled/timed-out flush acknowledges the sole error. Poll two overlapping flushes in both orders, then a third; test different-generation failures and one-record versus batch aggregation. Separately test a fully drained delivery `Timeout`/`Closed` versus an actual drain deadline/closure: abort may send EndTxn only after the former has drained, and commit/close must preserve their specified mappings.
4. Retire a worker before its first poll and during each detach/retry handoff; cancel worker, retry and cleanup tasks at explicit yield points; verify exactly one resource release, callback and result per accepted record, no cycle or lost ticket, and no stale wake. Repeat under shutdown and deliberate callback panic/blocked-callback policies.
5. Exhaust generation and active-flush bounds. Cancel the last fallback waiter before and after the old generation completes, race an attaching waiter, race close, and verify admission reopens only when legal. Pause an async admission immediately before registering for the generation wake and immediately after registration; rotate or reopen the same generation at each point and prove it neither sleeps past its deadline nor misses a wake. Keep one earlier record stuck while later records complete to confirm retained memory does not grow without bound.
6. Use loom or another bounded interleaving model for register/seal/finish/report/reopen and explicit atomic-order assertions; then use hosted native tests and real broker tests. Measure records/s, CPU, allocation counts, p50/p99, many producer threads, zero-byte records, sticky/non-sticky routing, batch sizes, abort pressure and flush churn against a pinned baseline. Compare the atomic-Arc option with the simpler lock-based reference. There are no results yet.

## Sketch limitations

[epoch-prototype.rs](epoch-prototype.rs) is a standalone one-generation illustration, SHA-256 `c43af2f82bf920b532ee029cb56dda22489f265ba31e38d20e601674b9df52cc`. Its source includes four deterministic Rust test scenarios. Only `rustfmt --check` was run; it was not compiled or tested. The sketch lacks channel permits, async cancellation ownership, resource/callback cleanup, multi-generation rotation, error acknowledgment, retention bounds, pause/reopen, notification and shutdown. Its drop records an accounting error but cannot perform the real record cleanup, so it must not be imported as the fix.

[check_model.py](check_model.py) (SHA-256 `889c097a140d4162e602e4beca47d9b40a46107dffd0f9bc43ff58c6ae06e003`) explored 734 abstract states and 1,711 transitions for two records and two ordinary rotating flushes. It models each operation as ideal and atomic; it does not test Rust, Tokio, resource ownership, a broker or the generation-cap fallback.
