# Independent review: producer flush design

Reviewed snapshot: `reviewed-DESIGN.md`, SHA-256 `ee557a3418de68b63db44254e39e0f9b4a10dc277577cc1d715508a7d5c2911d`. The standalone `epoch-prototype.rs` was inspected at SHA-256 `c43af2f82bf920b532ee029cb56dda22489f265ba31e38d20e601674b9df52cc`. The source paths in the report were checked against producer source at `86f285c706645e68146737a243707953c524b89d`. This is a source-only review, not validation of an implementation, the hosted artifacts, or the model's coverage. Some mitigations below were added to the design during review; they still need implementation and tests.

The proposed generation accounting is a useful direction, but the document and sketch are not sufficient to adopt a producer fix. In particular:

1. **CAS-to-handoff wake race.** A sender registers in generation G, then pauses before `Permit::send`. Flush seals G, wakes a worker and that worker consumes the wake with an empty queue. The sender finally enqueues, but a counter-only worker sees no new flush signal and can wait for its normal linger. A covered record can miss an intended forced drain. Carry and check the generation/cutoff on dequeue, or use a proven post-handoff seal/re-notification protocol. A deterministic test must stop the sender at that exact point and also cover retries.
2. **Pause/reopen and admission wakes need explicit state ownership.** An async sender must enable a notification before rechecking the publication state and a monotonic change sequence, including reopen of the same Arc and permanent close. When fallback waiters A and B cover paused G, A may complete and publish G+1 before B is dropped; B's stale guard must not reopen G or overwrite G+1. The revised draft calls for these rules, but the state machine, bounds and races are not implemented or model-checked. Include concurrent close, last-waiter cancellation, attachment and successful fallback.
3. **Error claim must not get lost in panic or internal close.** Performing no `await` between cursor advancement and `Ready` prevents ordinary async cancellation in that segment, but fallible work or a panic there can still consume the only error. Prepare the returned error and next epoch before claiming; `Error::Io::clone` currently formats an inner error and can panic. Separately, `close` currently awaits `flush_until`, then awaits shutdown and maps non-timeout delivery errors to `Ok(())`. A close canceled during shutdown could advance the shared cursor without a caller seeing the error. Define whether close is an observer, when it acknowledges, and how its existing public mapping is preserved.
4. **Flush acknowledgment is not transaction state.** A transactional record may expire in the pending path without setting the current abort-required flag. If a user flush observes and acknowledges that failure, a later `commit_transaction` cannot rely on an empty flush cursor to prove the transaction succeeded. Terminal transactional outcomes need a transaction-generation-scoped abortable/fatal state that survives flush observation until the appropriate abort/identity transition; commit must recheck after its drain. A normal flush cutoff also permits newly accepted records after its cutoff. Commit and abort need a transaction admission fence across draining and `EndTxn`, while allowing already accepted retries, or those later records can race the transaction boundary.
5. **Ownership and resource closure are not solved by the ticket sketch.** A ticket drop that decrements a count cannot by itself release the buffer/sticky reservation or finish callbacks and the oneshot. The proposed owned cleanup supervisor, reserved capacity, synchronous fallback, panic handling, cancellation of batch-local vectors and shutdown need a concrete ownership proof. Completion and admission bookkeeping must also be ordered around the actual handoff: queue/sticky metrics or reservations updated only after send can otherwise lag a worker that has already completed the record.
6. **Bounds and timeout wording need precision.** A cap on accepted tickets/cleanup entries does not bound caller-owned inputs, arbitrarily many pre-admission send futures, or `send_all`'s pre-collected records. A blocking interceptor on a single-thread runtime can stop the executor that must poll the flush timer; its deadline is not necessarily enforced while that thread is blocked. Include these limits, overflow handling for monotonic identifiers/cursors, and an explicit callback reentrancy policy.

The abstract Python model assumes operations such as admission, rotation and reporting are already atomic. Its result does not cover the cap fallback, wake race, transaction lifecycle, callback behavior or resource cleanup; it cannot validate the above. The Rust sketch was not compiled or run in this review. No native tests, Cargo builds, broker tests or benchmark were run, and the root checkout was not modified.
