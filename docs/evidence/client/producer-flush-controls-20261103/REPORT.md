# Producer flush: source review and regression controls

Base: `45cbff24de76490594970fc962cd04e7be9fafb1`, `src/producer.rs` (copied as `producer-before.rs`, SHA-256 `4f461c00864e3da5e20925796c1f489580a4046202cffd86fefeb64cbd145a32`). Line numbers below refer to that commit. These are source-derived findings, not results from running the tests.

The controls ask for a stronger desired behavior: a successful `flush` must not precede the terminal outcome of an already accepted record, and a canceled flush must not consume its only failure report. The source says that `try_send` delivery is observed on `flush` (3195, 4015–4018); current documentation also states qualifications and limitations. The implementation's worker snapshots and retry counter do not establish the stronger behavior. The controls test that behavior; their expected failures should not be read as proof of a current documented-contract or Java compatibility violation. Do not qualify delivery/flush correctness based on this source analysis alone.

## Source-derived paths

- **Worker pending expiry and sticky cohort cancellation:** `purge_expired_pending` (7660–7686) calls `fail_kept_batch(..., Timeout)` for a nonempty expired set without `note_fail`. `take_sticky_batch` (7619–7624) similarly fails a canceled cohort without recording the error. Failures do increment error metrics, invoke interceptors, and resolve any per-record sender through `fail_kept_pendings` (11379–11403), but a `try_send` record has no sender; `Worker::take_fail` (7411–7422) can therefore return `Ok(())` for that failure.
- **Expired after batching:** after the record batch is encoded, `fire` checks `now_inst >= batch_deadline`, fails the groups, and returns `Ok(())` without `note_fail` (8286–8290). This is distinct from expiry in the pending vector.
- **Expiry during requeue:** both `requeue_pendings_sync` (8951–8955) and `requeue_pendings` (9009–9015) call `fail_pendings(..., Timeout)` then continue without `note_fail`. Their full/closed queue branches do record an error (8976–8985, 9031–9040), illustrating the inconsistent disposition.
- **Retry actor terminal errors:** `RetryGuard::drop` fails its held record (6738–6749), including on early return from `retry_one` after a deadline, metadata failure, closed producer, or cancellation (6858–6980). `RetryBatchGuard::drop` directly fails remaining records (6703–6735), and `RetryReceiver::drop` fails queued records (6594–6607). None publishes a worker's `fail`; `RetryCountGuard` decrements `retries_out` after these paths (6682–6701), allowing flush to see zero retries and return success. These guards have no remaining link to the original worker's local `fail`.
- **Retired worker invisible before handoff:** `retire_worker_nudge` removes the worker from `nodes` and closes admission (6229–6245). `fire` invokes it before taking/requeuing owned pending/in-flight batches (8020–8026, 8049–8052, 8281–8284, 8302–8310). `requeue_pendings` can yield before incrementing `retries_out`, notably in `detach_pending_chunks` (8992–9006, 9029, 11408–11418). Separately, a worker can be retired before its spawned future first runs; accepted records then remain in its data channel. Both `flush_workers` snapshots enumerate only `nodes` (3503–3520), and `flush_until` checks only those snapshots and `retries_out` (4027–4045). On a current-thread runtime, retire an unpolled worker after a successful `try_send` and poll flush before yielding: the snapshots are empty, the retry count is zero, the record is still buffered, and flush can return `Ok(())`. `live_workers` counts retired workers for shutdown but is not used by this flush barrier.
- **Canceled flush consumes a failure:** control handling calls `tx.send(self.take_fail())` (7905–7913; also Worker drop 7400–7404). Argument evaluation takes the error before `send` discovers a dropped oneshot receiver. Thus a flush canceled after control enqueue but before the worker reply can consume the only stored error; the next flush returns success. With multiple workers, `flush_workers` returns at the first error via `result?` (3535–3542), dropping other receivers; their already-sent or later-sent errors may likewise be consumed unobserved. A worker can also disappear with its local `fail` if no control receiver is queued.
- **Close has its own contract:** `close` and `close_timeout` deliberately return `Err` only for `Timeout`, turning other `flush` failures into `Ok(())` (4053–4076, 4079–4096). Any redesign must preserve that public behavior unless the API and documentation are intentionally changed.

The async failure and requeue helpers also place accepted `Pending` values in local vectors across yields: expiry splits them out before `recompute_pending_estimate().await` (7669–7685); `fail_kept_pendings` awaits while owning the batch (11379–11403); requeue owns detached chunks across yields (8992–9048). Task cancellation can drop those locals outside `Worker::drop`, so fixing the barrier also requires reviewing and guarding those ownership transitions, buffer reservations, callbacks, and delivery outcomes. This is a source-level cancellation risk requiring deterministic tests, not a tested runtime result here.

## Fix obligations

A collection of local `note_fail` calls does not fix actor ownership, worker retirement, or canceled receivers. A redesign needs one explicit admission/completion invariant that spans successful enqueue, pending, in-flight, retries, retired workers, cancellation, and shutdown. Capture the flush cutoff at a point linearized with successful admissions; complete each accepted record exactly once only after terminal outcome publication and required resource/callback work. Include zero-byte records and rejected, canceled, or partially admitted sends correctly. If allowing later records, either track a generation/frontier or document and validate stronger wait-for-quiescence semantics, including continuous traffic. Do not use `buffered_bytes` or `live_workers` as a stand-in: zero-byte records, early resource release, and long-lived idle workers make them unsuitable.

A canceled/timed-out flush must not acknowledge an error on behalf of its caller. Decide and document how overlapping flushes and multiple failures are reported; coordinate error publication, completion, and barrier observation without an await between irrevocable error consumption and return. Preserve the existing separate delivery-timeout and caller-flush-timeout behavior even though both currently use `Error::Timeout`. Cover sticky and non-sticky routing, successful acks and `acks=0`, per-record send futures, empty batches, rejected admissions, retry transfer/cancellation, multiple workers, shutdown, and duplicate/lost completion under panic/cancellation. Measure any per-record atomic, lock, allocation, and cache cost on representative producer workloads before asserting a performance improvement.

## Isolated controls

`regression-controls.patch` (SHA-256 `dcb7fa244056a3ccad7c81ba38611e5cb2157d4a7bdfbe8245cedad2cdfd0c03`) adds four tests only:

1. An accepted `try_send` record expires in pending and must make `flush` report `Timeout`.
2. An actual flush future is polled until its control is queued and then dropped; an injected terminal record error must remain visible to the next flush.
3. An accepted record remains in an unpolled retired worker; a single immediate poll must not report successful flush while metrics show it is not terminal.
4. An accepted record is handed to `RetryGuard`; its terminal drop and retry-count release must remain visible to flush even when there is no published worker.

The tests use real `try_send` and `flush` methods; test 4 directly constructs the retry guard to pin the otherwise timing-sensitive ownership boundary. The socket peers intentionally do not implement Kafka: these cases expire, inject a pre-write failure, or are held before worker polling. The timeout test uses a zero delivery timeout to make expiry deterministic. Tests assert error counts and released bytes to distinguish terminal delivery failure from the flush deadline. They require independent review and hosted execution both before and after any actual fix. The unmodified base is expected to fail the assertions by source analysis; that expectation has not been executed or verified here.

`rustfmt --edition 2021 --check` passed for the copied test source; `git apply --check` passed against a separate copy of the pinned source. No Cargo/native build or test was run in the low-space workspace. The patch does not modify production code and is not a fix.
