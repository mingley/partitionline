# AddPartitions retry deadline and cancellation evidence

The source-only AddPartitions coverage candidate remains unapplied. These controls used a local mock coordinator and a test-only scheduling checkpoint; they do not establish live-broker failure recovery or public enqueue behavior.

On commit `b631809f0e03ba6f65f808e51d8e47e3fd9380d1` plus the frozen coverage patch, [run 42441684902](https://github.com/mingley/partitionline/actions/runs/42441684902) compared two expiry schedules. Natural retry-backoff expiry returned broker code 51 and left the transaction abort-required. When the checkpoint crossed the deadline after the final backoff check, the next loop returned Timeout and left the transaction error state healthy. Both synthetic worker-owned records received Timeout, their two reserved bytes were released, transaction-partition identities were removed, and their sequences rewound. Both default and all-feature profiles reproduced the distinction. The run succeeded because it required the crossing control to fail its abort-required assertion. Earlier [run 42441500093](https://github.com/mingley/partitionline/actions/runs/42441500093) stopped at test compilation: the coverage patch had removed an import still used by new coordinator tests.

An isolated narrow repair was then tested against commit `264322ff430b0594f4c3864e53dcd832de2a930b` plus the same coverage patch in [run 42443855811](https://github.com/mingley/partitionline/actions/runs/42443855811). The uninstrumented repaired producer source had SHA-256 `b03577efa883ea0bd162c2af71db0618aa3d3bfd8e49819b6a55a788757a9fa8`. In both profiles, natural expiry, forced deadline crossing, per-record Timeout, normal cleanup, and preservation of a prior fatal cause passed.

The cancellation control in that run failed in both profiles. It canceled `Worker::fire` after the abortable disposition was recorded but before partition cleanup: both record completion channels closed without a result, both reserved bytes remained counted, and both transaction-partition identities remained registered. The transaction still reported an abortable error. The checkpoint makes this specific schedule reproducible, but the synthetic test does not prove how public producer shutdown or every cancellation path behaves. The narrow repair remains unapplied and must not be treated as cancellation-safe.

[Raw control logs](https://github.com/mingley/partitionline/actions/runs/42443855811/artifacts/13602422605) include both feature profiles. No benchmark, transaction-generation, or production-readiness claim follows.

## Additional source observations

The following observations concern [main at `374dcf4`](https://github.com/mingley/partitionline/blob/374dcf45db20ee728b00c0b0188e77ca1f47fa9c/src/producer.rs). Except for the single-record helper witness below, they are source observations without separate cancellation controls. They do not change the AddPartitions result above.

- [Batch draining and grouping](https://github.com/mingley/partitionline/blob/374dcf45db20ee728b00c0b0188e77ca1f47fa9c/src/producer.rs#L7529) can move records out of the worker's pending queue and then yield. [Grouping](https://github.com/mingley/partitionline/blob/374dcf45db20ee728b00c0b0188e77ca1f47fa9c/src/producer.rs#L9569) can also hold records in local groups or scratch buckets. [Worker drop](https://github.com/mingley/partitionline/blob/374dcf45db20ee728b00c0b0188e77ca1f47fa9c/src/producer.rs#L7413) processes the queue and in-flight batches but does not inspect those intermediate owners.
- [Failure cleanup](https://github.com/mingley/partitionline/blob/374dcf45db20ee728b00c0b0188e77ca1f47fa9c/src/producer.rs#L11432) takes ownership across cooperative byte counting and chunking. The byte-count walk yields even for one record. Cancellation before the buffer release or before record completion can therefore affect ownership at a different point from the AddPartitions checkpoint. Requeueing and sticky batch selection have similar ownership transfers.
- [Sequence rollback](https://github.com/mingley/partitionline/blob/374dcf45db20ee728b00c0b0188e77ca1f47fa9c/src/producer.rs#L10305) rewinds only when the allocated range is still the tail. A later allocation can leave an unresolved sequence prefix; cleanup cannot claim general sequence recovery without handling that ordering.
- Existing [synchronous failure cleanup](https://github.com/mingley/partitionline/blob/374dcf45db20ee728b00c0b0188e77ca1f47fa9c/src/producer.rs#L11375) walks records and invokes user interceptors. Putting it directly in a drop guard would make drop cost proportional to batch size. An interceptor panic can interrupt the remaining completions; a second panic during unwinding can abort the process. A design must account exactly once for buffer bytes and record outcomes, including cancellation and callback unwinding, while respecting worker and transaction lifetimes.

[Run 42444842648](https://github.com/mingley/partitionline/actions/runs/42444842648) independently exercised `fail_kept_pendings` directly with one synthetic record on the `374dcf4` source and Rust 1.99.1 x86_64. In both feature profiles, one manual poll reached its existing cooperative yield; dropping the future then closed the result channel and left one byte reserved. A normal completion through the same helper returned Timeout and released the byte. The run passed because it asserted the current behavior as a witness, not because the bug was fixed. It did not exercise public producer shutdown, an interceptor panic, or sequence handling. The original source hash was `e21d03f495f504f167bc56139dc03798b0f323ca51370c7dceade23a2dad066e`; the source with the added test was `f4845e2dd5ccedaaee63e4954c759d778ebe76cb25a95e7eebde247961742cbb`. [Control logs](https://github.com/mingley/partitionline/actions/runs/42444842648/artifacts/13603560215) contain both profiles. The first workflow attempt, [42444812925](https://github.com/mingley/partitionline/actions/runs/42444812925), failed validation before starting a job because an artifact expression was malformed.

A guard limited to the coordinator await would not cover these other ownership transfers. The retry repair and the AddPartitions coverage patch remain unapplied. Transaction-generation ordering, already-admitted operations, sequence recovery, and bounded cleanup remain open.
