# AddPartitions response qualification

This capsule contains a source-only producer candidate. It is not adopted or qualified, and no benchmark or production-readiness claim follows. The workflow runs on an x86_64 GitHub-hosted runner when this capsule or its workflow changes on `main`, and can also be started manually. This capsule was prepared without running the workflow.

The candidate patch is pinned to SHA-256 `5e356bd2d7616354de4a3e60ebd23bd12104bc4a9d8a29cc65cbd258f38d8cfe` and repository commit `45cbff24de76490594970fc962cd04e7be9fafb1`. It adds request-bounded validation of AddPartitions responses, fatal and abortable error precedence, deterministic retry routing, and a terminal state on cancelled or invalid response validation. The public first-error decoder remains unchanged. The candidate also retains the coordinator's current rediscovery behavior for LOAD-only responses.

The workflow checks out this capsule and the exact source commit separately using sparse checkouts. It verifies the runner, patch, witness, source and supporting source hashes. It temporarily inserts the same two test-only mock-socket witnesses into the base and patched source. On the base, each must fail with its specific assertion: one detects success on an incomplete response and the other detects a mixed LOAD/fence response hiding the fence. On the candidate, the witnesses and six focused tests must pass with default and all features. The workflow also checks formatting of `src/producer.rs` and runs Clippy on the all-feature library. These are focused controls: they do not run the unrelated v18 or ReadCommitted validations, public producer integration, a real broker, TLS, SASL, benchmarks or the full suite.

Every command has a timeout and retains its raw log and result. Expected baseline failures are distinguished from compilation errors and timeouts. `summary.json`, command logs, version and source pins, and failure information are uploaded even on a failed check where GitHub Actions can run the upload step. The runner checks available space on each filesystem used by the checkout, outputs, Cargo home or Rustup home. It refuses to start below 1.5 GiB and polls during commands, stopping the process group if space falls below the floor. Cargo uses an exclusively created target directory under RUNNER_TEMP; the runner refuses a pre-existing target and removes it after a floor breach only if its open directory descriptor still matches the path. The runner requires GitHub Actions and the exact GITHUB_WORKSPACE/base checkout and RUNNER_TEMP output paths. A pinned Linux ownership helper retains the process leader until ordinary descendants in its session are stopped and reaped; it is not a sandbox against a subprocess that deliberately creates a new session. The workflow checks space before and after checkout and toolchain installation; those GitHub actions are not continuously monitored, and polling cannot guarantee that a fast write never crosses the threshold between samples.

The transaction coordinator lock is still released before response validation. Other operations already in flight may still send while validation is pending. The existing `unsent_txn_partitions` temporarily removes the pending set across a yield and can lose it on cancellation. The decoder guard protects the terminal flag after response validation starts; it does not establish end-to-end cancellation safety or transaction ordering. The candidate parses a non-retried response twice and its performance cost is unmeasured. These limitations and broader interoperability, security, durability, resource and performance gates remain open even if this workflow passes.
