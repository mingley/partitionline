# TLS provider assessment

Assessment date: 2026-11-08. Repository source: [`d314151e6718ffb2172bf9297728724216401099`](https://github.com/mingley/partitionline/tree/d314151e6718ffb2172bf9297728724216401099). This is a read-only source and documentation review, not a security audit, a build, an interoperability qualification, or a performance comparison.

No Rust-only provider reviewed here is currently qualified to replace the existing provider while retaining the project's general TLS and OIDC behavior. The release and upstream-source descriptions below are time-specific; they do not establish long-term maintenance or production suitability. The existing `ring` dependency means the all-Rust objective is not met. Keeping it preserves the current dependency choice; it does not establish overall production readiness.

## Repository observations

- The [client manifest](https://github.com/mingley/partitionline/blob/d314151e6718ffb2172bf9297728724216401099/Cargo.toml#L92) enables `ring`, `std` and `tls12` for rustls, and `ring` and `tls12` for tokio-rustls. Its lockfile resolves rustls 0.23.46, rustls-webpki 0.103.16, tokio-rustls 0.26.6 and ring 0.17.14. The client manifest blob is `4a90b08ab3fb886676231310b1f7132e04e2cfbb`; its lockfile blob is `96e364d34121fe90183f87f4f49fd92b883bc447`.
- [Client TLS setup](https://github.com/mingley/partitionline/blob/d314151e6718ffb2172bf9297728724216401099/src/net.rs#L534) attempts once to install ring as the process-wide provider and ignores an install failure. The [TLS builder](https://github.com/mingley/partitionline/blob/d314151e6718ffb2172bf9297728724216401099/src/net.rs#L688) therefore uses the process provider, which may already have been installed by the embedding application. It uses Mozilla roots or a supplied CA bundle, a server name, and an optional client certificate and key. The public `install_crypto_provider()` function exposes the process-default behavior. Changing to a per-config provider needs an explicit compatibility decision.
- The [broker manifest](https://github.com/mingley/partitionline/blob/d314151e6718ffb2172bf9297728724216401099/partitionline-broker/Cargo.toml#L10) has optional `tls`, `sasl` and `oidc` features. The listener [constructs a ring provider explicitly](https://github.com/mingley/partitionline/blob/d314151e6718ffb2172bf9297728724216401099/partitionline-broker/src/security/tls.rs#L177), including its required-mTLS verifier. It disables resumption and early data, and rotates configurations for new connections. The [OIDC HTTPS client](https://github.com/mingley/partitionline/blob/d314151e6718ffb2172bf9297728724216401099/partitionline-broker/src/security/oidc/http.rs#L386) also constructs ring explicitly. Broker manifest blob: `4e23c42f8d9ac722005098a4b58e1046b711e1a3`; broker lockfile blob: `19652acd96b929402b1e4a9394a33d12a7e69449`.
- OIDC independently enables the direct `ring` dependency and uses it for [RS256 and ES256 JWT verification and key fingerprints](https://github.com/mingley/partitionline/blob/d314151e6718ffb2172bf9297728724216401099/partitionline-broker/src/security/oidc/jwt.rs#L1). Replacing rustls's provider alone would not remove ring from an OIDC build. SCRAM also uses separate HMAC, PBKDF2 and SHA dependencies, so SASL behavior cannot be assumed from a TLS handshake alone.
- Existing [TLS fixture code](https://github.com/mingley/partitionline/blob/d314151e6718ffb2172bf9297728724216401099/tests/common/mod.rs#L4623) creates RSA-2048 server, CA and client identities. A provider that excludes RSA or TLS 1.2 would change supported configurations; it is not a transparent swap.

These observations come from manifests, lockfiles and source. A lockfile includes optional and target-specific dependencies; we did not run `cargo tree -e features` or inspect binaries for any target. The repository selects stable Rust and declares Rust 1.99; the [stable release at review](https://blog.rust-lang.org/2026/10/15/Rust-1.99.1/) was 1.99.1. Candidate MSRV declarations below are not a successful build against that toolchain.

Its authors describe it as very new; no project-specific security, compatibility or performance qualification was done. |

A provider that needs no C compiler is not necessarily free of assembly, `unsafe`, OS interfaces, or target-specific assumptions. Rustls's [third-party provider list](https://github.com/rustls/rustls/blob/0d7f9b323ec71c2f359c8e490a13a57e7b1a0f53/PROVIDERS.md) says those projects have not been evaluated by its maintainers. A recent release is evidence of activity, not a guarantee of ongoing maintenance.

## Qualification still needed

The following work was not run or audited as part of this assessment. Some existing tests may cover individual cases; their presence is not evidence of complete provider-migration coverage.

- Resolve the active dependency and feature graph for the client and broker, including `tls`, `sasl` and `oidc`, the intended target triples and an embedding application that installs its own provider. Inspect compiled artifacts and transitive build dependencies before claiming no C or assembly.
- Exercise TLS 1.2 and 1.3 with RSA and ECDSA server identities and certificate chains, both with and without required mTLS; test the supported key encodings, public and custom roots, hostname and IP verification, expired and untrusted certificates, handshake errors, no plaintext fallback, and certificate/configuration rotation. Include independent Kafka and TLS peers.
- Exercise PLAIN, SCRAM-SHA-256, SCRAM-SHA-512 and OAUTHBEARER over TLS, plus OIDC HTTPS trust and JWT RS256/ES256 verification, error paths and rotation. Preserve the broker's existing no-resumption/no-early-data policy and distinguish public-key verification from RSA private-key signing risks.
- Perform an independent security review of the exact provider and dependency versions, their maintenance and disclosure process, constant-time and platform assumptions, and any advisory applicability. Run current dependency advisory checks; this note is not such a check.
- Compare candidate and ring on the same x86_64 host using pinned builds, CPU features, TLS version, cipher, key type and workload. Measure handshake rate and latency, mTLS, encrypted record throughput, CPU and allocations. Provider self-reported microbenchmarks do not establish Kafka client or broker performance.

No provider, platform, feature matrix, OIDC flow, security claim or benchmark was independently built or tested for this note.
